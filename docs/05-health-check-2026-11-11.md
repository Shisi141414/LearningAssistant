## 1. 结论

现有框架适合继续增量构建，无需整体重写。Electron 主进程负责数据和模型服务，preload 暴露有限接口，React 负责界面；SQLite 迁移、共享类型、原文/整理双视图已形成基础。

**当前处于可运行原型阶段，尚不能视为日常课堂可靠版本。** 类型检查、现有测试和构建通过，隔离运行也通过，但存在对话响应不显示、数据迁移覆盖、中止生成丢内容等实际问题。应先做路线图 R0，再扩展材料和项目系统。本次交付体检、规划与仓库模型文件治理；下列业务缺陷尚未修复。

## 4. 问题清单

优先级：P1 为新增业务前应处理的核心功能/数据可靠性问题；P2 为应在相关功能扩展前处理的可靠性与边界问题。本次未确认 P0。下述“静态确认”表示已追踪代码路径，但尚无对应真实交互或外部服务实测。

### H01 · P1 · 未推送历史中包含大型模型包（本批治理）

- 证据：初始提交 `ae3e684` 加入 `sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20.tar.bz2`，大小 **511,274,346 字节（约 487.6 MiB）**；开工时远端 `origin/main` 尚无此文件。
- 影响：GitHub 普通 Git 文件上限为 100 MiB；仅追加删除提交或 `.gitignore` 不能消除早期提交中的大对象。[GitHub 官方说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
- 用户已明确要求不推送压缩包，压缩包和解压目录都加入 ignore。本批保留本地模型文件、为原历史建立本地备份，从未发布历史移除该文件，保留其余改动和提交元信息，再普通推送；不改远端已有历史、不强推。最终同步结果在交付回复中确认。

### H02 · P1 · 新对话的助手响应不会进入当前消息列表（已复现）

- 位置：`src/renderer/src/stores/chat.ts:95`、`:104`；主进程在 `src/main/ipc/chat.ipc.ts` 创建助手占位，但没有推送占位事件。
- 根因：前端发送时只加入用户消息；chunk/done 对现有消息执行 `map`，没有对应助手 ID 时不会插入。主进程占位落库不等于前端已有该消息。
- 复现：给 store 一个用户消息，依次调用 `appendChunk()`、`finishMessage()`；助手 ID 始终不存在，`streamingIds` 却曾包含它。重新打开会话才可能从数据库读到回答。
- 后续验收：首个 chunk 即创建/合并助手消息；完成事件在从未收到 chunk 时也能处理；切会话和停止生成不产生重复项。

### H03 · P1 · 存储迁移直接覆盖目标已有数据库（已复现）

- 位置：`src/main/services/storage.ts:44`、`:56`，及写配置后的重开路径。
- 根因：`copyFileSync(src, dst)` 没有目标冲突保护，迁移和恢复默认都可能覆盖已有库；先改引导配置再重开，新库打开失败时没有自动恢复旧配置。
- 复现：临时源文件 `SOURCE_MARKER`，目标文件 `EXISTING_TARGET_MARKER`，调用实际迁移函数后目标变为 `SOURCE_MARKER`。该探针覆盖的是文件策略，不表示完整 SQLite/WAL 恢复验收通过。
- 后续验收：目标已有库时拒绝或走明确的备份/恢复流程；验证路径、临时复制与数据库完整性后再切换；注入复制、配置写入、打开失败，旧库始终可继续使用。未来附件也要纳入同一数据目录迁移。

### H04 · P1 · 中止流式对话后已生成内容可能落成空串（静态确认）

- 位置：`src/main/ipc/chat.ipc.ts:176`–`:204`。
- 根因：`full = await streamChat(...)` 只有正常 resolve 才赋值；中途 abort 抛出时 `full` 仍是空串，chunk 回调只向界面转发，随后以空串写回数据库。
- 后续验收：在真实服务以外先用可控流输出多块后取消；重开会话必须保留已收到部分。还应区分主动取消、上游失败和窗口关闭。

### H05 · P1 · 课堂结束时未到断句点的尾句未落库（静态确认）

- 位置：`src/main/services/asr.ts:141`；`src/renderer/src/pages/ClassroomPage.tsx:244`。
- 根因：只有 `onFinal` 路径保存段落；`stop()` 直接清空 stream/events/lastText，没有 flush；结束课堂又切回 setup 并清掉 partial。直接离开课堂页同样需要梳理收尾顺序。
- 后续验收：说到半句就结束课堂、暂停录音、切页、关闭窗口时，验证尾句保存策略及完成确认；不要在启动自动录音之后才订阅第一批识别事件。

### H06 · P2 · 加密不可用时静默改为明文存 Key（静态确认）

- 位置：`src/main/services/secrets.ts:10`–`:22`。
- 根因：`safeStorage` 不可用时写入 `plain:` 前缀的明文 Buffer，与架构中“始终加密”的约定不一致；此检查没有读取任何实际密钥。
- 后续验收：加密不可用时明确报错或提供明确的临时会话策略，不能静默持久化明文；兼容处理历史 `plain:` 记录并说明重新配置/迁移状态。

### H07 · P2 · Anthropic SSE 错误被当成成功吞掉（已复现）

- 位置：`src/main/services/llm.ts:149`–`:155`。
- 根因：收到 `type: error` 后主动抛错，但外层 JSON 解析的 `catch` 同时吃掉它。网络返回 HTTP 200 也可能在流内报错。
- 复现：本地 mock `fetch` 返回合法的 `event: error`，错误内容 `quota exceeded`；`streamChat()` 实际 resolve 空串，没有 reject，未发出任何真实网络请求。
- 后续验收：流内 error 正常上报；同时覆盖 LF/CRLF、跨网络块事件、尾块、取消及超时。解析失败与上游业务错误分开处理。

### H08 · P2 · 切块会改变原文顺序，并突破长度上限（已复现）

- 位置：`shared/textChunk.ts:35`–`:55`。
- 根因：遇超长句时直接推入硬切块，没有先输出缓冲 `cur`；带 overlap 拼接下一句时也没有再次约束总长度。非法/非整数 `maxChars`、overlap 还缺少输入约束。
- 复现 A：`chunkText('前文。' + '长'.repeat(30) + '后文。', {maxChars:10, overlap:0})`，第一块是“长…”而“前文。”跑到最后。
- 复现 B：两个各 10 字符的句子，`maxChars:10, overlap:3`，输出长度为 `[10, 13]`。
- 后续验收：检查内容顺序、逐块长度、重叠区及边界参数；仅比较总字符数不能证明内容完整。带位置的教材条目依赖本项先修复。

### H09 · P2 · AI 异步整理可能覆盖期间的人工编辑（静态确认）

- 位置：`src/main/ipc/classroom.ipc.ts:119`–`:132`；`notes.ipc.ts` 的手动段落更新。
- 根因：等待模型响应后无条件 UPDATE；没有检查输入版本、原始文本或是否已被用户改过。数据库连接也跨越异步模型等待被缓存，期间切换数据目录需要协调。
- 后续验收：生成期间手动改稿或迁移数据后，旧响应不能覆盖新内容或继续向已关闭连接写入；保存候选或标记冲突。原架构 ADR-1 提到的手动修改保护字段尚未落地。

### H10 · P2 · IPC 与外链的运行时边界未达到文档约定（静态确认）

- 位置：`src/main/ipc/helpers.ts:17`、各 handler、`src/main/index.ts:30`。
- 根因：`handleResult` 只包装异常，不验证 sender、枚举、文本长度、文件路径等；TypeScript 类型在运行时不阻止错误载荷。外链直接交给 `shell.openExternal(url)`，缺少协议白名单和导航约束。
- 后续验收：对来自受信页面的 IPC、字段范围和资源大小作集中验证，非法请求不产生写入或原生异常；外链限制允许协议。现有 contextIsolation、nodeIntegration=false 和 CSP 是已有保护，本次未证明存在远程利用链，不将边界缺口直接描述为已发生的入侵。

### H11 · P2 · 离线整理失败没有持久化待补跑状态（静态确认）

- 位置：`src/main/ipc/classroom.ipc.ts:17`、`:94`–`:138`；`ClassroomPage.tsx` 的 `triggerOrganize`。
- 根因：进行中状态只存在内存 `Set`，失败只 toast 并保留原文；没有持久化 pending/failed、重试次数和恢复队列。重复整理请求返回早期结果，也不走正常完成事件。
- 后续验收：离线新增段落重启后仍知道哪些待整理，联网后按用户设置补跑；重试幂等且不会覆盖人工编辑，进度能够结束或明确失败。

## 5. 现有测试为什么没有发现这些问题

类型检查能验证“传的字段是什么类型”，无法证明“界面中已有助手消息”；构建验证代码能产出文件，也不能证明“停止时保存了已经收到的文本”。目前三组测试侧重纯函数和基础数据库结构，没有覆盖跨进程事件、可取消流、文件迁移冲突与课堂生命周期。

后续针对真实风险补测试：消息的创建→流式更新→终止，迁移的成功/冲突/回滚，音频尾段收尾，教材块的顺序与稳定来源。既有样例测试保留，但不能把全部绿灯等同于产品验收。

## 6. 后续构建建议

1. **先完成 R0**：先对话可见性与数据安全，再中止/收尾、错误传播、待处理状态和边界校验。每项先保留可复现用例，再修根因。
2. **把材料导入提前到 R1/R2**：先让每条内容能稳定指回教材位置，再交付人工校准的课堂分屏，随后增强自动对齐。
3. **共用知识引用与任务系统**：项目通过知识关联帮助学以致用，日程与备忘共用同一任务 ID；不要各做一套互不相通的“待办”和“截止时间”。
4. **明确自动化的控制范围**：自动分类和排程按启用规则运行，保留来源、理由、撤销与待补全状态；提醒需要持久化，退出应用后的能力要有实际执行机制。

完整阶段和验收已写入 [路线图](03-roadmap.md)，本报告不启动四组大功能的实际实现。

## 7. 给继续开发者的阅读顺序

先看 `shared/types.ts` 理解学科、活动、笔记段落、引用和事件；再看 `src/main/db/migrations.ts` 理解真实数据约束；沿 `src/preload/index.ts` → `src/main/ipc/*` → `src/main/services/*` 跟一次请求；最后看 React 页面与 zustand store 如何订阅结果。

尤其留意三个区别：数据库里有表不代表功能已实现；主进程有消息不代表前端有对应状态；当前教材游标不等于历史笔记的永久来源位置。后续扩展时，这三个边界会直接决定功能是否可靠。
