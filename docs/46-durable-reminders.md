# 持久提醒、通知投递与后台驻留

日期：2026-11-13 · codex

## 用户入口与能力范围

- 设置 → 提醒：启用学习提醒、系统通知、默认开始/截止提前量、全天日程基准时间、补发窗口、系统通知免打扰、关闭窗口后后台驻留，以及测试系统通知。
- 日程 → 提醒中心：待处理、待提醒、历史，支持知道了、稍后提醒、完成任务和手动重试系统通知。稍后支持 5/10/30/60 分钟或明天此时（24 小时后）。
- 已保存日程 → 任务提醒：独立启停和提前量；留空跟随全局，0 表示到点。学习时间块沿用开始提前量。未保存的任务提醒受日程编辑关闭、切换和元数据保存保护。

应用内提醒默认启用，系统通知与后台驻留默认关闭。默认开始提前 10 分钟、截止提前 60 分钟，补发窗口 120 分钟，全天日程以本机当天 09:00 为基准再减去开始提前量。界面时间与提醒免打扰均按本机时区。

完成任务、删除任务、改期、移除时间块或停用任务提醒后，旧的待提醒/待处理条目及其系统投递失效。阻塞任务仅保留截止提醒，暂停/归档项目不再提醒。任务删除时提醒记录随外键级联删除；这不是独立的永久审计档案。

免打扰只延迟系统通知，应用内记录照常保存；结束后合并仍有效且未处理的提醒，修改或关闭免打扰立即按新设置检查。关闭系统通知会跳过尚未发送的记录，重新打开不会自动重发这些旧记录；可在提醒中心明确重试。

后台驻留开启后，关闭窗口将隐藏到托盘，课堂记录和其他进行中的工作继续运行；托盘可打开原窗口或彻底退出。**彻底退出、关机、未登录时不能发送提醒**。没有新增开机启动、系统计划任务或延迟关机设置。重启/休眠恢复后，在补发窗口内的未发布提醒合并处理，超窗项进入历史。

## 开源复用与选择依据

按“直接使用 → 迁移 → 修改 → 自己写”的顺序核对：

| 方案 | 依据与选择 |
|---|---|
| [Electron Notification](https://www.electronjs.org/docs/latest/api/notification) | 直接使用已有运行时创建通知，处理 show/failed/click。isSupported 仅表示系统支持，不能证明用户看到横幅。 |
| [Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)、[Tray](https://www.electronjs.org/docs/latest/api/tray) | 直接复用 resume 检查与托盘驻留；不依赖 Windows 不提供的 shutdown 事件来持久化提醒。 |
| [node-notifier](https://github.com/mikaelbr/node-notifier) | 已比较其 Windows SnoreToast 路线；目前 Electron 已覆盖所需运行中通知，无证据要求另带通知程序，因此未引入新二进制与依赖。 |
| [Electron 社区 Windows 通知问题 #51650](https://github.com/electron/electron/issues/51650) | 作为版本兼容性验收线索，不把历史问题直接当成本项目当前故障。 |
| [Windows 通知要求](https://www.electronjs.org/docs/latest/tutorial/notifications) | 使用与打包配置一致的 AppUserModelID；正式安装的开始菜单快捷方式和实际系统通知展示另行验收，开发模式不能代替。 |

SQLite、Temporal、任务及日程实体均直接复用，未新增依赖。自行实现部分仅为本项目的持久提醒规则、去重身份和投递状态机；没有自行实现系统通知后端。

## 为什么把提醒与系统通知分开保存

数据库提交和外部系统展示不能组成一个原子事务。如果发送途中关机，程序可能无法知道系统到底是否展示。简单地“重启后重发”可能重复，而先标记成功可能漏报。

本批追加迁移 **27**，不修改已有迁移：

- `reminder_settings` / `task_reminder_options`：全局与任务覆盖配置，独立乐观修订。
- `reminders`：开始、截止和学习时间块的持久身份及应用内处理状态。
- `reminder_deliveries`：系统投递的待发送、已领取、系统确认展示、失败、状态不确定、跳过与取消。
- `reminder_change_counter` 与触发器：任务、项目状态、时间块或配置变化即失效缓存，包括同一毫秒内多次修改。

身份由任务、事件种类、实际来源、事件时间及提前量决定。单纯锁定或重命名不会生成另一条提醒；改期会使旧身份失效，生成新身份。已发布/已处理身份保留去重墓碑，稍后提醒使用独立子记录并继承原事件身份。未发布的失效项若恢复原时间且仍在补发范围，可重新启用。

先提交应用内记录，再领取系统投递并落盘，然后调用 Notification.show。只有系统 show 回调才标记“系统已确认展示”；15 秒没有展示结果、或重启发现领取中断，标记“状态不确定”，不自动重复投递。用户可明确重试，界面提示可能重复；每次重试使用新 attempt，旧回调不能覆盖新结果。**不宣称系统外部副作用严格一次，也不宣称 show 证明用户已阅读。**

每 30 秒以及启动、休眠恢复时检查。单批最多发布/合并 1000 项，活跃数据限五千任务、一万块；超过限制显示运行错误且保留已有记录。变更时在主进程做有界同步事务，未变更时使用计数器缓存；不是任意规模的后台调度服务。
